# trajectory-eval

Automatically derive behavior contracts and execution reports from OpenTelemetry (OTLP) distributed traces.

Given a recorded OTLP trace (a JSON file with `resourceSpans → scopeSpans → spans`), `trajectory-eval` maps spans onto a canonical step sequence and generates two structured artifacts:

- **BehaviorContract** — deterministic, step-agnostic invariants that describe what the system *must* do (data dependencies, tool sequences, parameter types, output formats, etc.)
- **ExecutionReport** — behavioral observations and performance metrics (latency budget, tool output utilization, redundancy rate, cycle detection, etc.)

## How it works

Spans are classified into step types by a precedence chain:

| Condition | StepType |
|---|---|
| `status.code == 2` | `error` |
| No `parentSpanId` | `service` |
| Kind 3 or 4 (CLIENT/PRODUCER) | `execution` |
| Kind 2 (SERVER) with CLIENT/PRODUCER parent | `execution_result` |
| Kind 1 (INTERNAL) | `operation` |

Rules are then generated by `HardRule` subclasses:

| Rule | What it checks |
|---|---|
| `DataDependencyRule` | Value- and type-based data flow between tool outputs and subsequent inputs |
| `ToolSequenceRule` | Which tool pairs appear in sequence and whether the ordering is consistent |
| `ToolParamCountRule` | Each tool receives exactly the observed number of parameters |
| `ToolParamTypeRule` | Each parameter has the expected Python type |
| `ToolResultTypeRule` | Detected content type of each tool output (JSON, XML, Python, file path, …) |
| `TerminalStateRule` | Whether the trace reaches a valid terminal state |
| `MutationMatcherRule` | Whether the system adapts after a failed or empty tool result |
| `ToolOutputUtilizationRule` | Whether tool outputs are consumed by later steps |
| `RedundancyRateRule` | Fraction of duplicate tool calls stays below threshold |
| `CycleBreakRule` | System does not repeat the same tool+args combination within a short horizon |
| `LatencyBudgetRule` | Per-step latency stays within budget |

Rules are passed through an emitter (producing `CompiledRule` instances), a deduplicator (merging identical rules, flagging conflicts), and assembled into the final contract and report by `ContractCompiler`.

## Installation

Requires Python 3.10+.

```bash
pip install -e ".[dev]"
```

No API keys or network access required. All analysis runs locally.

## Usage

```bash
python eval_otlp.py healthy-checkout-otlp.json
```

Output is a JSON object on stdout:

```json
{
  "contract": { "schema_version": 2, "rules": [ ... ] },
  "report":   { "metrics": [ ... ], "flags": [ ... ] }
}
```

A step-by-step trace summary is printed to stderr before the JSON result.

## Running tests

```bash
pytest
```

## Project layout

```
otlp_parser/
  models/           # Pydantic models: Trace, Step, Tool, BehaviorContract, ...
  generator/
    rules/          # One HardRule subclass per behavioral aspect
    emitter.py      # HardRule -> CompiledRule conversion
    deduplicator.py # Merge identical rules, detect conflicts
    contract_compiler.py  # Orchestrates the full pipeline
    report_builder.py
    hard_rules_otlp_config.yaml  # Rule configuration (YAML)
  parsers/          # OTLP trace parser
    parameter/      # Tool input parameter type detection
eval_otlp.py        # CLI entry point
healthy-checkout-otlp.json  # Example OTLP trace
```
